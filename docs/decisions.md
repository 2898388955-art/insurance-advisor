# 设计决策记录（ADR）

每个模块都必须回答四件事：解决什么问题、为什么选这个方案、与其他方案对比、代价与边界。

---

## D-01 文档解析：MinerU

**① 问题**　条款 PDF 有双栏、表格、页眉页脚、多级编号。直接抽文字会丢标题层级，后续无法按章节切分，也无法做引用溯源。

**② 方案**　MinerU 4.2.1 本地模式（`--tier flash`），输出 Markdown + 页码标记。

**③ 对比**

| 方案 | 优势 | 劣势 | 适用 |
|---|---|---|---|
| PyMuPDF / pdfplumber | 秒级、轻量 | 无版面理解，标题层级靠正则猜 | 版式规整的纯文本 PDF |
| 云端文档 API | 效果最好、零运维 | 按页收费、依赖网络、别人跑不起来 | 商业产品 |
| PaddleOCR 自建 | 完全可控 | 开发量大 | 有算法团队 |
| **MinerU 本地** | 免费、离线、结构还原好 | 首次装模型重、CPU 慢 | 个人开源项目 |

**④ 代价**　模型 820MB；11 页 CPU 解析约 1 分钟；4.x 的 CLI 与网上 2.x 教程不兼容（必须 `mineru server start` 后 `parse --tier flash`），且**命令失败时仍返回 exit code 0**，脚本不能只看退出码。

## D-02 存储划分：MySQL + Milvus

**① 问题**　项目同时有结构化数据（产品、保费区间、分类）和非结构化数据（几万字条款）。全放向量库做不了范围筛选；全放 MySQL 做不了语义召回。

**② 方案**　MySQL 存业务字段与原文块，Milvus 只存向量和过滤字段；父子块分表；`doc_id` 由文件哈希派生；`vector_id` 回写子块表。

**③ 对比**

| 方案 | 优势 | 劣势 |
|---|---|---|
| 全放 Milvus | 一套系统 | 无事务/JOIN，改数据要动向量库 |
| 全放 MySQL | 强一致、简单 | 中文全文检索弱，无语义召回 |
| **MySQL + Milvus** | 各司其职、可分别扩展 | 需自己保证双写一致性 |

**④ 代价**　双写失败会出现「有块无向量」，用 `product_clause.status` + `ingest_task` 重试兜底；未加外键，脏数据要靠应用层拦截；父子块内容重叠，存储约翻倍（5 万字量级可忽略）。

## D-03 解析归一化：规则层

**① 问题**　MinerU 的 Markdown 是给人看的：章标题时有时无、小节编号和标题被拆成两行、表格每行重复 `| --- |`。直接切块会把 `7.1` 和 `年龄错误` 切成两个块，`heading_path` 完全不可用。

**② 方案**　`ai/app/ingest/normalize.py` 做三件事：
1. 识别四类标题（Markdown `#`、中文章节、独立编号行、行内编号），维护标题栈生成 `heading_path`
2. 合并被换行截断的标题（如 `2.2 保险期间与不` + `保证续保`）
3. 修复表格：去掉重复分隔线；两列表转成「键：值」文本（对检索更友好）

**③ 对比**

| 方案 | 优势 | 劣势 |
|---|---|---|
| 直接用 MinerU 输出 | 零开发 | `heading_path` 不可用，切分必错 |
| 换更高档位解析（standard） | 结构更准 | 需启用本地解析服务 + 下载 VLM 模型，链路更重 |
| **规则归一化** | 快、可解释、可迭代 | 规则需要针对文档类型调 |
| 用 LLM 重排结构 | 泛化好 | 每份文档一次调用，成本和延迟都高 |

**④ 代价与边界**
- 规则是启发式的，遇到版式不同的条款会掉准确率；当前 37 个章节识别出 31 个，6 个存在截断或缺失
- 已知失败：标题末尾的字被 MinerU 排到正文之后（如 `7.6 合同效力的终` + 正文 + `止`），规则层无法修复，只能靠换解析档位
- 判断依据是「短 + 无句末标点」，遇到超短正文（如「30 日」）可能误判为标题，已用「含数字不合并」规避
- 如果后续发现某类文档系统性失败，应升级为「按文档类型配置规则」而不是继续堆正则

## D-04 父子块切分与阅读顺序校正

**① 问题**　MinerU 在这份 PDF 上把**正文排在标题之前**，直接按标题归属内容会导致整本文档错位一格：`1.3 保险对象` 下面挂的是 `1.4 投保年龄` 的正文。RAG 一旦引用错章节，比答不出来更糟。

**② 方案**
1. **顺序检测**：对每个二级标题，比较"标题后第一段"与本标题、下一标题的字面重合度，投票决定是否存在整体错位；检测到就启用校正。
2. **校正**：把每段正文归给它的"下一个标题"，而不是前一个。
3. **父子块**：父块 = 二级标题下的整节（含标题文本）；子块 = 父块按段落切 400 字、60 字重叠，过短碎片（<20 字）过滤，但保证每个父块至少一块。

**③ 对比**

| 方案 | 优势 | 劣势 |
|---|---|---|
| 不校正，直接用 | 零成本 | 检索结果系统性错位 |
| 换 standard 档重新解析 | 根治 | 需本地解析服务 + VLM 模型，成本高 |
| LLM 判断每段归属 | 泛化最好 | 每份文档几十次调用，慢且贵 |
| **字面重合度投票 + 整体移位** | 一次判断，成本为 0 | 只适用于"整体错位"，混合顺序会失效 |

**④ 代价与边界**
- 检测是文档级的，假设整篇顺序一致；如果一份文档里部分章节正常、部分错位，会误判
- 依赖标题关键字出现在正文中；纯编号标题（如"3.1"无文字）会让投票失效
- 缺失标题无法凭空补出：本文档 `7.3`、`7.4`、`4` 没被识别，导致这几节的内容并入了相邻章节
- 当前结果：25 个父块、53 个子块，平均 249 字。关键小节（`2.3 等待期`）已确认内容正确

## D-05 切块策略：标题优先 + 合并 + 递归兜底

**① 问题**　固定长度切分会把条款拦腰截断；纯按标题切又会产生大量只有标题的碎片，超长章节也会让子块失去上下文。

**② 方案**（本文件实测数据支撑）
1. **父块边界 = 一级/二级标题**：条款的语义单元就是"章 > 条"，标题即边界。
2. **过短合并**：父块 <150 字时并入同章相邻节。实测 25 个父块中 9 个 <150 字（最短 8 字），合并后降到 2 个，中位数从 224 → 365 字。
3. **超长递归**：父块保持整节用于回填，子块按 400 字 / 60 字重叠递归切；单段超长再按句子切。实测最长父块 3665 字，必须有这一层。
4. **三级标题按需升级**：默认不当边界；若某节超过 800 字且内部有三级标题，才在三级标题处再分。

**③ 对比**

| 方案 | 优势 | 劣势 |
|---|---|---|
| 固定 500 字切分 | 简单、块大小均匀 | 切断条款条目，`heading_path` 无意义 |
| LangChain `MarkdownHeaderTextSplitter` | 现成、社区标准 | 丢失页码，无法做引用溯源 |
| 语义切分（按相邻句子向量相似度） | 边界更自然 | 每句一次 embedding，成本高且不稳定 |
| **标题优先 + 合并 + 递归兜底** | 边界可解释、保留页码与 heading_path | 依赖标题识别质量 |

**④ 代价与边界**
- 依赖 MinerU 的标题识别：37 个目录条目只识别出 31 个，缺失的 3 个章节内容会并进相邻节
- 合并规则是"同章内合并"，跨章短节仍会保留（当前还剩 2 个 <150 字的父块）
- 900 字以上的章节被递归切成多块后，单块可能缺少"这一节在讲什么"的概括，需靠父块回填弥补

## D-06 向量化与 Milvus 索引

**① 问题**　53 个子块要支持语义检索；中文保险术语多、同义表达多（"等待期" vs "观察期"），关键词匹配不够用。

**② 方案**
- Embedding：本地 **bge-m3**（1024 维），通过 Ollama 常驻服务调用
- 索引：Milvus 2.5.4，**HNSW（M=16, efConstruction=200）+ COSINE**
- 主键：直接复用 MySQL `clause_child.id`，便于幂等重灌与删除
- 字段：向量 + `text` + `heading_path` + `page_no` + `parent_id`，检索后无需回表即可展示

**③ 对比**

| 方案 | 优势 | 劣势 |
|---|---|---|
| OpenAI text-embedding-3 | 效果好、免运维 | 按量计费、需联网、数据出境 |
| 阿里云 embedding | 中文好、稳定 | 需账号与费用 |
| Milvus Lite（嵌入式） | 零部署 | **不支持 Windows**，本机无法运行 |
| `sentence-transformers` 直接加载 | 无服务依赖 | 每次脚本启动都要加载 1.2GB 模型 |
| **bge-m3 via Ollama + Milvus standalone** | 免费、离线、中文强、服务常驻 | 占内存，需维护一个额外进程 |

索引选 HNSW 而非 IVF_FLAT：当前只有 48 条，任何索引都能跑；选 HNSW 是为了数据到十万级时不用重建选型。代价是内存换速度——1024 维、10 万条约 400MB 原始向量，加索引开销约 1GB。

**④ 代价与边界**
- 纯向量对**精确编号/数字**不敏感（"2.5.1"、"30 日"），必须靠 BM25 混合检索补足，这是下一步
- bge-m3 1024 维比 768 维更占存储与算力，换的是中文效果
- Ollama 常驻约 1~2GB 内存；与 Docker 的 15GB 上限并存，31GB 物理内存够用
- 本节验收已通过：问"等待期是多久" top1 命中 `2.3 等待期`（score 0.758，page 3，正文含"30 日"）

## D-07 工程结构：模块化单体 + 三层架构

**① 问题**　业务模块只有 5 个（分类、产品、条款、对话、内部接口），单人开发；既要结构清晰，又不能让运维成本吃掉开发时间。

**② 方案**
- **一个** Spring Boot 应用（模块化单体），按业务分包：`category / product / clause / chat / internal / ai`，每个包内再分 `controller / service / mapper / entity / dto`
- 保留 Java 与 Python 两个进程：不是微服务，而是按技术栈拆（Python 依赖 MinerU/torch，与 JVM 不兼容）
- 服务间用 HTTP，不引入注册中心、网关、配置中心

**③ 对比**

| 方案 | 优势 | 劣势 | 适用 |
|---|---|---|---|
| 微服务全家桶（Nacos/Gateway/Sentinel） | 独立部署、独立扩缩容 | 运维与联调成本高，单机无收益 | 多团队、高并发 |
| 纯按层分包（controller/service/mapper 各一个大包） | 结构直观 | 改一个功能要跨多个包，包膨胀后难读 | 极小型项目 |
| **模块化单体 + 包内三层** | 改动内聚、可整包拆走、部署简单 | 模块边界靠约定维持 | 1~3 人团队 |
| Serverless | 免运维 | 冷启动、SSE 长连接不友好 | 事件型任务 |

**④ 代价与边界**
- 所有模块共享一个 JVM 与数据库连接池，某个模块的慢查询会影响全局
- 模块边界靠包结构和代码评审维持，没有编译期强制；后期若出现跨模块直接调 Mapper，需要引入 ArchUnit 之类的约束测试
- 将来若要拆服务，前提是把 `chat` 对 `product` 的调用改成接口而不是直接依赖 Mapper

## D-08 产品图片存储：对象存储 + 只存 key

**① 问题**　产品图体积大、数量随产品增长；放数据库会撑大备份并拖慢查询，放应用本地磁盘在容器重建或多实例时会丢。

**② 方案**
- S3 协议对象存储：本地 **RustFS**，生产可换阿里云 OSS / 七牛（同协议，只改 endpoint 与密钥）
- 数据库 `product_image` 表**只存 object key**，不存完整 URL
- 访问用**预签名 URL**（默认 60 分钟），bucket 无需公开读
- key 规则：`products/{productId}/{uuid}.{ext}`，避免中文名与覆盖
- 上传校验：文件头嗅探（jpeg/png/webp）+ 5MB 上限，仅看扩展名可被绕过

**③ 对比**

| 方案 | 优势 | 劣势 |
|---|---|---|
| 数据库 BLOB | 事务一致、备份简单 | 表膨胀、CDN 无法缓存 |
| 应用本地磁盘 | 实现最简单 | 容器重建丢失、多实例不共享 |
| base64 内联 | 无外部依赖 | 图片稍大接口就崩 |
| **对象存储 + DB 存 key** | 便宜、可 CDN、可换供应商 | 多一个依赖，需处理签名 |

**④ 代价与边界**
- 预签名 URL 每次访问都要走签名校验，高并发下应由 CDN 私有回源替代
- 上传接口 `/admin/**` 目前**没有鉴权**，只在本地开发可用，上线前必须加
- 没有做图片压缩与多尺寸缩略图：列表页加载原图会浪费带宽，后续应在上传时生成 400px 缩略图
- 删除产品时不会自动清理对象存储文件，需要补偿任务

## D-09 条款字段抽取：规则 baseline + 原子引用（采纳并修正后落库）

**① 问题**　`product` 的年龄、等待期、保证续保等字段是筛选与推荐的入参，但导入阶段刻意留空（源数据为「待核验」）。不做这一步，「结构化筛选 + 语义检索」只能停留在口号。

**② 方案**　规则抽取 + 严格 JSON schema + 逐字引用校验；只有 `confidence ≥ 0.5` 且 quote 能在所标页码原文中找到的字段才落库。落库增加 `verified_from / field_confidence / field_extracted_at` 三个溯源列，并新建 `product_field_quote` 存字段级页码与原文。

**③ 对比**

| 方案 | 优势 | 劣势 |
|---|---|---|
| 纯人工录入 | 最准 | 不可复现、无法溯源 |
| 纯 LLM 抽取 | 泛化好 | 每份一次调用，quote 易被改写，幻觉需逐条核 |
| **规则 + 校验 + 转人工** | 零成本、引用 100% 可回查 | 表述变体覆盖有限 |

**④ 代价与边界**
- 本轮 48 份中 18 份可自动落库，30 份转人工（14 份无条款原件、12 份附加险字段写在主合同、DOCX 无稳定分页、2 份低置信度）
- 逐字校验只能证明「引用是真的」，不能证明「值是对的」：H05/H06/T07 的 `min_age` 引文合法但值缺失，已人工修正
- 抽取时点早于 MinerU 产物生成，18 份输入为 PyMuPDF 降级，需第二轮重跑
- 前端只能对 `verified_from='clause_pdf'` 的产品展示字段，转人工产品的引用仅可用于溯源卡片

## D-10 产品查询模块：后端统一筛选与对比

**① 问题**　列表页、对比页、Agent 工具三处都要查产品。若各自拼 SQL/过滤条件，语义会漂移（比如列表按分类含子类，Agent 只查本级）。同时 48 条数据里大量字段为 NULL，筛选必须定义"未知值"的行为。

**② 方案**
- 单一 `ProductService` 提供 `search / detail / compare`，Controller 只做参数接收
- 分类筛选自动包含子分类（点「医疗险」能查到「百万医疗」）
- **NULL 宽松策略**：年龄/等待期/预算过滤时，字段未披露的产品仍然保留
- 对比结果在后端对齐成「行」，前端只渲染；空值统一显示"条款未披露"
- 图片在列表接口按页批量取主图并生成预签名 URL，避免 N+1 次对象存储调用

**③ 对比**

| 方案 | 优势 | 劣势 |
|---|---|---|
| 前端各自拼条件 | 后端简单 | 语义漂移，Agent 与页面结果不一致 |
| 后端返回 Entity | 省事 | 暴露内部字段，分类名/图片/标签要前端拼 |
| 引入 ES 做筛选 | 支持复杂相关性 | 48 条数据下纯属过度设计 |
| **MySQL + VO + 后端对比** | 语义统一、可复用 | 对比字段写死在代码里，新增字段要改代码 |

**④ 代价与边界**
- NULL 宽松过滤的副作用：**预算筛选项前完全无效**——48 个产品没有一个有保费数据，全部因"未知"被放行
- 前端需要靠「价格待补充」标签告知用户，不能假装有价
- 预签名 URL 每次列表请求都要签 12~50 条，CPU 成本可忽略，但生产应换成 CDN 直链
- 对比行硬编码在 `ProductService#compare`，新增对比维度必须改代码 + 发版

## D-11 价格展示：文案优先，不做数值筛选

**① 问题**　保险产品没有单一标价：同一产品的费率随年龄、性别、有无社保、等待期、保额、缴费方式变化；48 个产品里只有 29 个拿到了官方费率表，3 个只有保额表，2 个是行业示范条款，14 个没有费率资料。用「一个价格」建模必然误导。

**② 方案**
- 新增 `price_display`（展示文案）、`price_status`（PUBLISHED / NO_RATE_TABLE / NOT_PUBLIC / NOT_APPLICABLE）
- 未取得费率的一律写死 **「产品价格未公开」**，不显示费率区间，避免用户把它当成可投保价格
- **不做预算数值筛选**：费率口径有年缴、月缴、每万元保额、公式系数四种，直接比较会得出「0.02 元的意外险比 257 元的医疗险便宜」这种错误结论
- 对比页只显示「¥xxx 起 / 按费率表计价 / 价格未公开」三态

**③ 对比**

| 方案 | 优势 | 劣势 |
|---|---|---|
| 存一个 min/max 价格 | 筛选简单 | 口径不同，必然误导 |
| 用官方说明书案例保费 | 数字真实 | 仅 5 条，其中 3 条是"年交 20 万"的演示假设，不是产品价格 |
| 按费率表数值筛选 | 看似有数据 | 年/月/每万元保额混用，排序无意义 |
| **文案展示 + 状态标记** | 诚实、可解释 | 预算筛选暂不可用 |

**④ 代价与边界**
- 前端无法做「预算 3000 以内」筛选，只能展示价格说明；这是数据决定的，不是实现偷懒
- `price_display` 最长 114 字，卡片需要截断、详情页展开
- 若后续拿到标准化口径（如「30 岁男、有社保、计划一、年交」），可新增 `annual_premium` 字段再开放筛选

## D-12 前端视觉：金融杂志风格，自建组件

**① 问题**　保险产品信息密度高、决策链长。直接套电商模板（大红促销、倒计时、销量）会削弱金融产品需要的可信感；而 GitHub 上的 admin 模板在当前网络下拉取困难，且大多是后台管理风格，不适合 C 端。

**② 方案**
- 视觉语言：暖纸底色 + 墨蓝主色 + 黄铜点缀，中文衬线标题（宋体族）配无衬线正文
- 不套模板，基于 Element Plus 自建页面：产品库、详情、对比、对话四页
- 列表封面不用条款首页截图，改为**排版化封面**（品类字 + 大号汉字水印），把真实资料图放到详情页
- 对比页只高亮有差异的行，空值显示「未披露」
- 对话页预留「条款页码引用卡片」的版式，Agent 接入后直接填数据

**③ 对比**

| 方案 | 优势 | 劣势 |
|---|---|---|
| 电商促销风模板 | 转化视觉成熟 | 与金融可信感冲突，且同质化严重 |
| Element Plus 默认后台风 | 开发最快 | 无品牌感，像内部系统 |
| GitHub admin 模板 | 现成 | 当前网络不可达；偏后台，不适合 C 端 |
| **杂志风自建** | 差异化、信息层级清晰 | 样式维护成本高 |

**④ 代价与边界**
- Element Plus 全量引入，首屏 JS 约 1.1MB（gzip 379KB），后续应改为按需引入
- 目前只做了桌面端 + 基础移动适配，未做暗色模式和国际化
- 封面是程序生成的排版图，不是真实产品海报；真实图仍保留在详情页
- 对话页当前是静态演示，输入框禁用，等 Agent 接口接入后才可用

## D-13 Agent 编排：规则路由 + LangGraph 状态机

**① 问题**　用户问题分三类：查条款（RAG）、要推荐（产品筛选）、要比差异（对比）。用一个大提示词让模型自己决定，会出现路径不可控、引用丢失、失败无法降级的问题。

**② 方案**
- **规则优先的路由**：关键词判断意图（对比/推荐/寒暄/其他→RAG），模型不参与路由
- **LangGraph 状态机**：`router → retrieve/advisor/compare → generate → compliance`
- **分层**：`api`（协议） / `agents`（编排与提示词） / `services`（检索、产品、合规） / `llm`（协议适配）
- LLM 走 **OpenAI 兼容协议**，默认 `deepseek-flash`；密钥只从环境变量注入，不写配置文件
- 任何节点失败都降级：LLM 不可用时返回检索到的条款原文；产品服务不可用时明确告知

**③ 对比**

| 方案 | 优势 | 劣势 |
|---|---|---|
| 单 Agent + 大提示词 | 开发最快 | 路径黑盒、引用易丢、无法针对性降级 |
| LLM 做意图路由 | 泛化好 | 多一次调用、结果不稳定 |
| **规则路由 + 图编排** | 可解释、可测、易降级 | 新意图要改规则 |
| 微服务编排 | 隔离好 | 单人项目过度设计 |

**④ 代价与边界**
- 规则路由覆盖有限：问「这两个哪个更划算」能命中对比，但「帮我看看这个」会落到 RAG
- 对比需要产品上下文（`product_id`），否则只能提示用户先去选择
- SSE 目前是「生成完成后按 24 字分片下发」，不是真 token 流；要真流式需改 LLM 调用为 `stream=true`
- 会话历史由前端携带，尚未落库；traceId 未与 Java 的 `X-Trace-Id` 打通

## D-14 会话、记忆快照、真流式与职业推荐

**① 问题**　前端携带历史不可信（刷新即丢）；多轮追问里的「它/这款」无法消解；原先的 SSE 是生成完再分片，不是真流式；推荐没有利用职业这一关键变量。

**② 方案**
- **会话**：Java 提供 `POST /api/v1/conversations`，会话 ID 由前端持有
- **记忆快照**：`agent_checkpoint` 每轮保存 `intent / question / answer / citations / product_id / occupation` 的 JSON 快照；下一轮取最近 6 轮拼历史，并用快照里的 `product_id` 做指代消解
- **真流式**：LLM 调用改为 `stream=true`，逐 token 走 SSE；前端再加一层打字机队列，抵消网络合并
- **职业推荐**：职业关键词 → 险种分类（室内低风险→医疗+重疾；高风险外勤→意外+定期寿险），按分类分别检索后合并去重

**③ 对比**

| 方案 | 优势 | 劣势 |
|---|---|---|
| 前端传历史 | 实现快 | 刷新丢失、可伪造、超长截断 |
| LangGraph 官方 checkpointer | 标准 | 持久化后端是 SQLite/Postgres，与项目 MySQL 不统一 |
| **MySQL 快照表** | 统一存储、可审计 | 需自己实现取历史与指代 |
| 生成完再分片 | 简单 | 首字延迟高，不是真流式 |
| **token 流 + 打字机队列** | 首字快、观感稳定 | 需处理合规替换后的 final 覆盖 |

**④ 代价与边界**
- 快照只取最近 6 轮，超出部分不进入上下文；暂未做摘要压缩
- 指代消解只处理「上一轮关联产品」，多产品指代（「第二个」）尚未支持
- 职业规则是硬编码关键词表，新职业要改代码；职业分类未进入产品字段，无法做核保级判断
- 产品数据里部分产品没有年龄/价格字段，推荐会显式标注「未披露」

## D-15 会话历史与记忆摘要压缩

**① 问题**　快照只保留最近 6 轮，长会话更早的信息会丢失；前端需要会话列表与历史消息，但消息原先只存在 checkpoint 的 JSON 里，Java 无法直接查询。

**② 方案**
- **消息落库**：AI 每轮同时写入 `message` 表（user/assistant 各一条），Java 提供 `GET /conversations` 与 `GET /conversations/{id}/messages`
- **自动标题**：首轮问题截断 30 字作为会话标题，并刷新 `updated_at`
- **摘要压缩**：`conversation_summary` 表保存摘要与「已覆盖快照 ID」；当轮次 ≥6 且为 4 的倍数时，把最近 4 轮以外的历史压缩成 ≤120 字摘要
- **上下文组装**：下一轮 = 摘要（system）+ 最近 4 轮原文，而不是无限拼接历史

**③ 对比**

| 方案 | 优势 | 劣势 |
|---|---|---|
| 全量历史塞上下文 | 信息完整 | token 线性增长，超长后不可用 |
| 只保留最近 N 轮 | 实现简单 | 早期约束（预算、职业）丢失 |
| **摘要 + 最近原文** | 成本可控、保留关键约束 | 摘要会丢细节，需控制压缩频率 |
| 向量化历史检索 | 可按需召回 | 多一套索引，当前规模不值得 |

**④ 代价与边界**
- 摘要是 LLM 生成的，可能丢失细节或引入轻微改写；因此保留最近 4 轮原文兜底
- 每 4 轮触发一次摘要调用，长会话有额外 token 成本
- 摘要按会话单条覆盖，不支持多版本回溯
- 消息表尚未记录 token 数与耗时（字段已预留）

## D-16 设计 token 统一 + 需求表单 + 工具调用摘要

**① 问题**　各页面圆角、字号、按钮样式各写一套（2px/4px/8px/999px 混用），视觉不协调；对话页全靠自然语言收集需求，槽位缺失时反复追问；Agent 调了哪些工具对用户不可见。

**② 方案**
- **设计 token**：定义 6~14px 三档圆角 + 胶囊、7 档字号（12/14/16/19/24/32/44）、统一边框与阴影；组件只引用变量，不再写魔法值
- **需求表单**：年龄/职业/预算/家庭结构/关注险种五项，提交时拼成一句自然语言复用现有对话链路，不新增后端接口
- **工具摘要**：Agent 在 `prepare` 阶段记录 `tools[{name, detail}]`，随 SSE `meta` 事件下发，前端渲染为小胶囊 + 耗时

**③ 对比**

| 方案 | 优势 | 劣势 |
|---|---|---|
| 继续逐页调样式 | 灵活 | 每加一页就多一套不一致 |
| 引入完整设计系统/组件库换肤 | 规范 | 改造成本大，现有页面需重写 |
| **CSS 变量 + 有限 token** | 成本低、全局生效 | 需要约束后续新增代码 |
| 引入表单引擎（form-create） | 功能强 | 5 个字段不值得多一个依赖 |

**④ 代价与边界**
- token 靠约定维护，没有 lint 强制；新增页面仍可能写魔法值
- 需求表单只覆盖 5 个槽位，健康状况等仍需对话补充
- 工具摘要来自节点执行结果，历史消息未持久化 tools（重新打开会话看不到胶囊）
- 耗时是 prepare 阶段耗时，不含生成阶段
