# 保险顾问 Agent —— 项目计划书 v1.0

> 目标：用 5 周做出一个**能一键跑起来、有在线 Demo、有评测数据**的开源项目，2026 年 12 月前写进简历，正面冲击 2027 春招。
> 定位：不是"又一个 RAG Demo"，而是**Java 业务后端 + Python AI 服务的双栈工程实践**。

---

## 0. 先说三句实话（决定这个项目值不值钱）

1. **你截图里那段项目描述是全网流传的模板**，同届用的人不会少。面试官一眼就能认出来。所以我们的目标不是照着复刻，而是**做出一版"模板讲不出来"的东西**：真实业务链路、可量化的数据、能当场开 Demo。
2. **27 届在 2026 年 11 月已经是大四上**，秋招窗口基本收尾。所以计划必须分两刀：
   - **第 1 刀（2 周，MVP）**：能演示、能写进简历、能应付"你这个项目做了什么"。
   - **第 2 刀（再 3 周，打磨）**：评测数据、一键部署、README、Demo 视频 —— 这些才是开源项目"加分"的部分。
3. **不要做的比要做的更重要**（见 §8 范围裁剪）。简历项目死于"什么都想做，最后一堆半成品"。

## 1. 项目定义

| 项 | 内容 |
|---|---|
| 中文名 | 保小顾 · 保险顾问 Agent |
| 英文名 | `insure-advisor`（GitHub 仓库名，好读好搜） |
| 一句话 | 面向普通用户的保险智能顾问：能查条款、能推荐产品、能横向对比，答案可溯源到条款原文 |
| 核心能力 | 条款问答（RAG） / 需求画像 + 产品推荐（Agent + 工具调用） / 多产品对比（结构化 + LLM 解读） |
| 差异化 | ① Java+Python 双栈 ② 结构化筛选与语义检索融合 ③ 答案引用溯源 ④ RAG 评测数据 ⑤ 合规审查 Agent |
| 目标用户 | C 端用户（自用/帮父母买） |
| 合规声明 | 仅用于学习研究，不构成投保建议；产品条款均来自公开渠道；答案强制附免责声明 |

### 与截图模板的区别（面试时最该讲的）

| 模板做法 | 我们的做法 | 为什么更值钱 |
|---|---|---|
| 全部 Python 一把梭 | Java 管业务与数据，Python 只做 AI | 展示工程分层与跨服务协作，不是"一个人的脚本" |
| 只有向量检索 | 结构化条件（预算/年龄/险种）+ 语义检索融合 | 真实推荐场景里，用户说"3 千以内保到 60 岁"是 SQL 问题，不是向量问题 |
| 只答不验证 | 60 条评测集 + recall/MRR/faithfulness 曲线 | 能讲"我怎么知道它变好了"，这是应届生里极少见的 |
| 无出处 | 每条结论带 `[1]` 引用，可跳转条款原文 | 金融场景刚需，演示效果最强 |
| 无风控 | 合规审查 Agent 拦截"保证续保""稳赚不赔"等表述 | 行业理解 + 安全意识的信号 |

**一次典型请求的链路（面试可复述）：**

```
用户："我30岁程序员，预算3000，想买份重疾险"
  → Vue 发 SSE 请求 → Java 建/取会话，落库 user message
  → Java 调 Python /chat（带 session_id + 历史摘要 + 内部签名）
  → LangGraph: 意图识别 = 产品推荐
  → 需求槽位：年龄30✓ 预算3000✓ 险种重疾✓ → 缺失：家庭结构/健康告知
  → 反问一轮（或按保守假设继续，需在 UI 标明假设）
  → 顾问 Agent 调 Tool: search_products(险种=重疾, 预算<=3000, 年龄=30)
        ↳ 该 Tool 实际打 Java 内部 API /internal/products/search（MySQL 结构化筛选）
  → 对 Top3 产品调 RAG Agent 各检索一段"保障责任"条款 → 生成推荐理由
  → 合规审查 Agent 过一遍 → 加免责声明
  → 流式吐出 token → Java 转发 SSE → 前端逐字渲染 + 引用卡片
  → 落库 assistant message + citations + token 成本
```

## 3. 模块拆解

### 3.1 保险类别模块（Java 主体）

**分类树**（一级 → 二级，够用即可）
```
意外险     ├ 综合意外 / 交通意外 / 少儿意外
医疗险     ├ 百万医疗 / 小额医疗 / 高端医疗
重疾险     ├ 定期重疾 / 终身重疾
寿险       ├ 定期寿险 / 终身寿险
年金/储蓄  ├ 教育金 / 养老金
旅行险     ├ 境内 / 境外
家财险     ├ 家财综合
```

**产品 PRD 关键点**
- SPU（产品）+ 条款版本（同一产品多版本迭代，条款文件带版本号与生效日期）
- 产品结构化字段：承保年龄、保障期限、缴费期、免赔额、保额、等待期、健康告知条数、是否保证续保、保费区间
- 每个产品挂 1 份主条款 PDF + N 份附加条款，**条款是最重要的 RAG 语料**
- 分类页支持筛选（险种 / 年龄 / 预算 / 保额），走 MySQL + 索引

**条款入库管线（这是全项目最值得讲的技术点之一）**
```
上传 PDF → MinerU 解析(Markdown) → 按三级标题切父块
        → 父块再按 200~400 token 切子块（递归 + 重叠 15%）
        → 子块 embedding → Milvus；子块文本 → ES(BM25)
        → 父块原文 + 元数据 → MySQL
        → 任务状态机：PENDING → PARSING → CHUNKING → INDEXING → DONE/FAILED
```
- 任务异步化（`@Async` + 状态轮询），前端有"解析进度"
- 幂等：同一 `doc_hash` 重复上传直接复用向量
- 元数据必须带：`product_id / doc_id / heading_path / page_no`，否则后面没法做过滤和溯源

### 3.2 Agent 模块（Python 主体）

**LangGraph 拓扑**
```
START → router(意图识别)
  ├─ 条款问答 → rag_agent → compliance → END
  ├─ 产品推荐 → profile_collect(槽位) → advisor_agent(tool calling) → compliance → END
  ├─ 产品对比 → compare_agent(结构化对比 + LLM 差异解读) → compliance → END
  ├─ 闲聊/超出范围 → chitchat / 拒答模板 → END
  └─ 风险表述(如"帮我隐瞒病史") → refuse → END
```
- **意图识别**：一次轻量 LLM 分类（JSON 输出）+ 规则兜底（含"对比""哪个好""多少钱"关键词）
- **槽位收集**：`age / budget / 险种 / 家庭结构 / 健康状况 / 已有保障`，缺失超过 2 个才反问，否则带默认假设继续并在回答中声明
- **Tool Calling**：`search_products` / `get_product_detail` / `get_clause_section` / `compare_products`，其中前三个通过 HTTP 回打 Java（带内部签名头），**这是双栈的实证**
- **多轮记忆**：最近 6 轮原文 + 更早内容压缩成 200 字摘要（Redis 存，DB 落档）
- **流式**：LangGraph `astream_events` → SSE，事件类型区分 `token / citation / tool_call / done`（前端能显示"正在查询产品库…"）

### 3.3 RAG 子系统（Python）

| 环节 | 选型 | 说明 |
|---|---|---|
| 解析 | MinerU | 表格/条款版式友好，能保留标题层级；备选 PyMuPDF+自写规则 |
| 切分 | 三级标题父块 + 递归子块 | 父子块策略：召回用子块，回填用父块 |
| Embedding | 本地 `bge-m3`（推荐）/ 阿里云 text-embedding-v3 | 本地模型 = 零成本 + 可离线 Demo，简历上更好讲 |
| 向量库 | Milvus standalone | 简历关键词，且支持标量过滤（按 product_id 过滤） |
| 关键词 | Elasticsearch 8 `ik_max_word` | BM25 解决"轻症豁免""保证续保"等术语精确匹配 |
| 融合 | RRF（k=60） | 两路各取 top20 融合 |
| 重排 | `bge-reranker-base`（可选，第 4 周做） | 有它，评测指标能明显上一档 |
| 缓存 | Redis：embedding by `md5(text)`，TTL 7d | 截图里那招保留，但要做成本统计表佐证 |
| 上下文 | 父块回填 + 去重 + 长度预算 | 命中子块 → 取父块 → 相邻块扩展 |

**引用溯源**：每个 chunk 带 `doc_id + page_no + heading_path`，模型被要求输出 `[[cite:chunk_id]]` 标记，后端解析成结构化 citations 返回给前端渲染卡片，点击弹出条款原文并定位到页。

### 3.4 工程能力模块（让项目从"能跑"变成"能看"）

- **SSE 流式**：Java `SseEmitter` 透传，处理超时/断连/客户端取消
- **可观测**：`traceId` 贯穿 Java↔Python 日志；`llm_call_log` 表记录模型、tokens、耗时、成本；前端 debug 面板可看
- **成本**：README 里出"单次问答平均 token / 成本"表格，配合缓存命中率
- **测试**：Java 单测（Service 层）+ AI 端 pytest（切分、RRF、prompt 解析）
- **部署**：`docker-compose.yml` 一键起 MySQL/Redis/Milvus/ES + 三服务；`.env.example` 齐全
- **CI**：GitHub Actions 跑 lint + 单测（不跑需要 API Key 的用例）
- **文档**：架构图、时序图、数据库 ER 图、API 文档（Swagger / FastAPI docs）

## 4. 数据模型（MySQL）

```sql
category(id, parent_id, name, code, sort, level)
product(id, category_id, name, company, code, min_age, max_age,
        min_budget, max_budget, period, waiting_days, guaranteed_renewal,
        highlights, status, created_at)
product_clause(id, product_id, doc_id, version, effective_date, file_url, status)
clause_parent(id, doc_id, product_id, heading_path, content, page_from, page_to)
clause_child(id, parent_id, doc_id, heading_path, content, token_cnt, page_no, vector_id)
conversation(id, user_id, title, intent_hint, created_at, updated_at)
message(id, conversation_id, role, content, intent, token_in, token_out, latency_ms, trace_id)
message_citation(id, message_id, chunk_id, product_id, score)
ingest_task(id, doc_id, product_id, status, err_msg, started_at, finished_at)
llm_call_log(id, trace_id, scene, model, tokens, cost, latency_ms)
```

Milvus collection：`clause_child_vec(id, doc_id, product_id, parent_id, embedding[1024], text)`
> Milvus 只存向量 + 过滤字段，文本和父块从 MySQL 回填 —— 这是"父子块"落地的具体分工。

## 7. 简历文案（可直接用，但建议自己再改两句）

> **保险顾问 Agent · 智能投保咨询系统** | 个人开源项目 | Java · Spring Boot · Python · LangGraph · RAG | 2026.11–2027.01
>
> - 设计 **Java 业务后端 + Python AI 服务** 双服务架构：Spring Boot 负责产品/分类/会话/条款版本管理，Python FastAPI 承载 RAG 与 Agent 编排，通过 SSE 打通流式对话，`traceId` 贯穿双服务链路；

> - 工程化：Redis 缓存 embedding 与高频问答（命中率 41%，单次问答成本下降 xx%）、Docker Compose 一键部署、GitHub Actions CI、60 条评测集与自动化指标回归。

（数字等做完后填真实值 —— **绝对不要编**，面试官会追问怎么测的。）

**面试高频追问，提前准备：**
1. 为什么用两个检索系统？→ 术语/条款编号精确匹配 vs 语义泛化，用真实 bad case 举例
2. 父子块为什么不直接把父块向量化？→ 父块太长导致语义稀释，召回归一化后分数不可比
3. RRF 为什么比加权分数融合好？→ 两路分数量纲不同，RRF 只用排名，无需调参
4. Java 为什么还要存在？→ 业务事务、权限、数据一致性；AI 服务无状态易扩缩；也便于将来接管理后台
5. 怎么评估效果？→ 评测集构造方法 + 三类指标 + 消融实验
6. 怎么控制成本？→ 缓存 + 小模型做路由 + 只对 top-k 做重排

## 8. 范围裁剪：明确**不做**什么

- ❌ 不做真实投保/支付/保单管理（合规风险 + 无价值）
- ❌ 不做复杂 RBAC / 多租户（一个简单 JWT 就够）
- ❌ 不做微服务全家桶（Nacos/Gateway/Sentinel 一律不要，双服务已经是亮点，注册中心纯属自嗨）
- ❌ 不做爬虫大规模抓取（法律风险；用公开条款 + 手工录入 20~30 个产品足够）
- ❌ 不做移动端 / 小程序（Vue 响应式即可）
- ❌ 不做花哨动效（前端 3 个页面 + 一个聊天窗，干净即可）

| 风险 | 影响 | 对策 |

| 合规/法律 | 中 | 只用公开条款、标注来源、全站免责声明、不提供投保链接 |

## 12. 交付规范：每个模块必须附带设计说明

> 这是项目的硬性约定。代码只是交付物的一半，另一半是"为什么这么写"。

每完成一个模块，必须给出四段式说明，并同步写入 `docs/decisions.md`（按模块编号，例如 `D-03 父子块切分`）：

| 段落 | 必须回答的问题 |
|---|---|
| ① 要解决什么问题 | 不写方案先写问题：这个模块存在的理由是什么，不写会怎样 |
| ② 为什么选这个方案 | 具体到约束：数据规模、延迟预算、团队熟悉度、成本 |
| ③ 与其他方案对比 | 至少列 2 个被否掉的方案，说清在什么条件下它们更好 |
| ④ 代价与边界 | 这个方案牺牲了什么、什么规模下会撑不住、将来什么信号出现时该换 |

**反例（不要这么写）：**
- "因为业界常用" —— 等于没解释
- "性能更好" —— 好多少？在什么数据量下？测过吗？
- 只讲优点不讲代价 —— 面试官一追问就露馅

**正面例子（父子块切分）：**
> ① 条款文档里"等待期 90 天"这种关键信息往往只出现在某一小段，但回答需要上下文。整段召回会稀释语义，切太碎又会丢上下文。
> ② 因此子块（200~400 token）负责召回，命中后回填父块（整节）给模型。
> ③ 对比：纯固定长度切分会切断条款条目；纯父块向量化会让相似度分数趋同，召回率下降。
> ④ 代价：存储翻倍（父块 + 子块）、回填增加一次 MySQL 查询；语料超过百万级时父子块映射表需要单独优化。
